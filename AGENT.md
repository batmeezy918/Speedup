# Speedup Benchmark Agent Protocol

## Purpose

This file is the operational contract for any human or AI agent conducting benchmark work in the batmeezy918/Speedup repository.

The repository contains research code and evidence. Benchmark execution MUST preserve the distinction between:

- formal proof
- implementation
- empirical measurement
- historical evidence
- hypothesis
- unsupported claim

The governing rule is:

> CLAIM STRENGTH MUST NEVER EXCEED EVIDENCE STRENGTH.

Simulation, benchmark execution, or repeated numerical agreement does not by itself establish a theorem, asymptotic result, universal claim, SOTA claim, quantum advantage, or physical law.

---

## 1. Non-Negotiable Rules

1. Never fabricate benchmark results.
2. Never fabricate versions, commits, hashes, timings, memory measurements, hardware identities, or solver capabilities.
3. Never silently replace a requested baseline with another implementation.
4. Never compare different mathematical problem instances as if they were the same instance.
5. Never compare outputs without independent correctness verification.
6. Never call an implementation SOTA merely because it beats one comparator.
7. Never infer asymptotic superiority from finite measurements.
8. Never convert a simulation result into a formal proof.
9. Never use historical benchmark numbers as if they were newly reproduced measurements.
10. Never mix quantum simulation evidence with evidence for quantum computational advantage.
11. Never overwrite historical evidence. Preserve it and label it as historical.
12. Never modify unrelated repository files while preparing or running a benchmark.
13. Every benchmark run must have a unique RUN_ID.
14. Every benchmark artifact must have provenance sufficient for independent replay.
15. If a dependency or baseline is unavailable, report it explicitly instead of substituting it.

---

## 2. Evidence Classes

Use these exact evidence labels where applicable:

- PROVEN_FORMAL — established by a formal proof accepted by the repository's proof boundary.
- FORMALLY_VERIFIED — mechanically checked result, but scope must be stated.
- EMPIRICALLY_VERIFIED — independently reproduced by executable tests under documented conditions.
- REPRODUCED — prior result reproduced under materially equivalent conditions.
- IMPLEMENTED — executable implementation exists and has been inspected/tested.
- HISTORICAL_ARTIFACT — result exists in a prior artifact but was not generated by the current run.
- HYPOTHESIS — proposed claim requiring further validation.
- UNSUPPORTED — no adequate evidence currently establishes the claim.

Do not collapse these categories.

Every benchmark run MUST record:

- RUN_ID
- repository
- Git commit SHA
- dirty/clean working-tree state
- benchmark script SHA256
- benchmark configuration SHA256
- machine identity
- OS
- kernel
- architecture
- CPU model
- CPU core/thread count
- RAM
- compiler and version
- compiler flags
- runtime versions
- dependency versions
- dependency commit SHAs
- relevant environment variables
- date/time
- matrix/problem family
- dimension
- seed
- canonical input-instance SHA256

If a field cannot be measured, write UNKNOWN; do not guess.

---

## 4. Canonical-Instance Rule

Competitive solvers MUST consume the exact same canonical problem instance.

For GF(2), the canonical object is at minimum:

~~~
A
b
problem dimensions
field = GF(2)
instance metadata
~~~

Serialize the canonical instance once.

Hash it.

Every solver receives that exact serialized instance.

Do NOT permit each solver to regenerate its own random matrix.

Do NOT include instance generation time in solver time unless the benchmark explicitly defines an end-to-end metric. If end-to-end time is measured, report generation and solve components separately.

---

## 5. GF(2) Competitive Benchmark

### Required competitors

Current primary competitive track:

1. OMEGA/AGD projection implementation.
2. M4RI / libm4ri.
3. CryptoMiniSat as an XOR/SAT baseline.
4. Any recovered historical bit-packed implementation, but only if its actual source/executable is recovered.

The historical bit-packed benchmark numbers may be cited as HISTORICAL_ARTIFACT until the implementation is recovered and independently rerun.

Do NOT reconstruct a replacement and label it as the historical implementation.

### Correctness

Every solver output must be independently verified by an implementation that is not simply trusting the solver's return status.

For a returned solution x:

~~~
A*x mod 2 == b
~~~

must be checked.

Record:

- solver status
- solution existence
- residual
- solution hash
- verification status

Where the problem has a known unique solution, record that fact explicitly.

Where multiple solutions are possible, do NOT require identical solution vectors. Compare solution validity and, where relevant, canonicalize the solution space or verify an appropriate basis.

### M4RI

M4RI must be treated as an independent optimized dense GF(2) baseline.

Record:

- official upstream URL
- exact version/tag
- exact commit
- build configuration
- compiler
- compiler flags
- exact API used
- matrix orientation
- solve semantics
- linkage mode

Do not assume API semantics. Inspect the installed headers/source and verify with a known small system.

### CryptoMiniSat

CryptoMiniSat is a separate XOR/SAT baseline.

Record:

- exact release/tag
- commit
- build configuration
- encoding of GF(2) equations
- variable ordering
- clause/XOR counts
- solver configuration
- preprocessing configuration if changed

Do not represent CryptoMiniSat as a dense linear-algebra baseline. It answers a different algorithmic pathway and must be labeled accordingly.

---

## 6. Timing Protocol

At minimum measure:

- input generation
- canonical serialization
- solver time
- independent verification
- total end-to-end time

The primary competitive metric must be explicitly identified.

Use monotonic high-resolution timing.

Warm-up behavior must be documented.

For very short runs, use repeated trials or batched execution so timer resolution does not dominate.

Record:

- trial count
- min
- median
- mean
- standard deviation when meaningful
- max

Do not report only the fastest run when making comparative claims.

Do not use wall-clock timing as a universal machine-independent property.

---

## 7. Scaling Protocol

Run multiple dimensions.

Never infer scaling from a single n.

For GF(2), maintain separate families such as:

- structured/local
- adversarial/dense
- additional families only when explicitly defined

Keep seeds deterministic.

For every dimension/family combination record the full instance identity.

If exhaustive enumeration becomes computationally infeasible, stop that comparator and report the boundary. Do not fabricate extrapolated brute-force timings.

The existing historical values such as 81,294x and 62,142x are historical evidence and must not be silently relabeled as current measurements.

---

## 8. Required GF(2) Ablation

Where practical, use the following decomposition:

~~~
A = exhaustive enumeration
B = standard GF(2) elimination
C = bit-packed GF(2)
D = OMEGA/AGD
E = M4RI
F = CryptoMiniSat
~~~

The current repository may not contain every implementation.

Missing implementations must remain explicitly marked missing.

Do not manufacture A/B/C/D/E/F completeness.

For OMEGA/AGD, separate:

~~~
T_detect
T_quotient
T_projection
T_solve
T_verify
T_total
~~~

when those stages exist.

This is necessary to determine whether any observed speedup comes from the mathematical projection itself, preprocessing, instance structure, implementation engineering, or another component.

---

## 9. Solution Identity

Use SHA256 receipts for canonicalized solutions.

For unique solutions:

~~~
solution_hash_OMEGA == solution_hash_M4RI
~~~

is strong evidence of matching output.

For non-unique systems, identical solution hashes are NOT required. Instead verify:

~~~
A*x = b mod 2
~~~

and compare the appropriate solution-space representation.

Never use output equality as a substitute for mathematical verification.

---

## 10. Quantum / SIC Benchmark Track

The quantum track is independent of the GF(2) competitive track.

Candidate components include:

- Hilbert/operator representations
- 30-operator SIC construction
- reciprocal operator construction
- A0 = I + Delta
- Aepsilon = A0 + epsilon V
- A -> A^-1
- E = A + A^-1
- K = A - A^-1
- E^2 - K^2 = 4I under the stated operator assumptions
- F_t(A) = Tr(exp(-tA) - exp(-tA^-1))
- normalized response functions
- R0/R1/R2/... response hierarchy
- reciprocal-spectrum/null-response tests
- RGCF/Xi spectral experiments
- SIM2XR shuffle experiments

Numerical agreement is empirical evidence only.

Do not claim a new physical law, holographic identity, quantum advantage, or universal response theorem without a proof or appropriate physical/experimental evidence.

### Numerical reporting

Record:

- dimension
- dtype
- precision
- tolerance
- random seed
- epsilon
- t values
- condition number where relevant
- inversion method
- eigensolver method
- residual norm
- invariant residual
- library versions
- hardware

Never silently loosen tolerance until a test passes.

If an invariant expected to equal 1 is measured as 0.999341, report the residual:

~~~
|1 - 0.999341| = 6.59e-4
~~~

and do not label exact invariant preservation unless separately established.

### RGCF/Xi

If an iterative run reports an intermediate Xi value and a different final Xi value, record both.

Example:

~~~
intermediate Xi = 2
final Xi = 0.834242
~~~

This must be explained by the implementation before it is interpreted as a physical or mathematical transition.

### SIM2XR

A shuffle failure such as:

~~~
103 relations
10 shuffle attempts
still degenerate
~~~

is a failed test of the current shuffle procedure, not evidence that degeneracy is mathematically intrinsic.

When diagnosing degeneracy, record what remains invariant across shuffle attempts.

## 11. AGD / Quotient Claims

For any AGD instantiation, distinguish:

~~~
implementation
formal theorem
empirical observation
domain-specific validation
~~~

The generic AGD framework does not automatically prove its validity in a new domain.

For a proposed equivalence, explicitly identify:

~~~
s1 != s2
Omega(s1) = Omega(s2)
C(s1) = C(s2)
~~~

and then establish the claimed quotient relationship.

If measurement preservation is claimed, identify the measurement map and prove or test:

~~~
M(s1) = M(s2)
~~~

for the specified observable class.

If reconstruction is claimed, provide the reconstruction map and receipt.

## 12. SIM2XR Rule

SIM2XR simulations do NOT upgrade claim strength by themselves.

A valid RIMS artifact should preserve, where applicable:

- RUN_ID
- input identity
- code identity
- assumptions
- invariants
- operators
- operator chain
- outputs
- residuals
- counterexamples
- failures
- environment
- manifest
- SHA256 receipts
- replay information

## 14. Claim Gate

A benchmark may state:

### EMPIRICALLY VERIFIED

only when:

- the executable was actually run
- the canonical instance is identified
- correctness was independently checked
- the environment is recorded
- the result is reproducible from preserved artifacts

### COMPETITIVE

only when the named competitors were actually executed on the same canonical instances.

### SOTA

This label is prohibited by default.

A benchmark result must not declare SOTA merely because it wins against the local comparator set.

If a broader SOTA question is relevant, report the exact tested comparator set and state:

~~~
SOTA STATUS: NOT ESTABLISHED
~~~

unless an independent, comprehensive basis exists.

### NEW ASYMPTOTIC ALGORITHM

Do not make this claim from benchmark timing.

An asymptotic claim requires mathematical analysis.

### QUANTUM ADVANTAGE

Do not make this claim from classical simulation.

---

## 15. Failure Is Data

A failed benchmark is a valid benchmark result.

Examples:

- dependency failure
- solver crash
- timeout
- incorrect solution
- invariant residual above threshold
- degenerate shuffle
- numerical instability
- inconsistent solution hash
- missing comparator
- insufficient memory

Record the failure.

Do not delete or hide failed trials merely because they weaken a claim.

---

## 16. Agent Operating Procedure

Before execution:

1. Inspect repository state.
2. Read this file.
3. Read relevant benchmark-specific documentation.
4. Identify exact implementation paths.
5. Identify exact dependency versions.
6. Check whether the working tree is clean.
7. Create a unique RUN_ID.
8. Freeze benchmark configuration.
9. Hash configuration and relevant scripts.

During execution:

1. Use canonical inputs.
2. Record every solver invocation.
3. Capture stdout/stderr.
4. Verify every result independently.
5. Preserve failures.
6. Do not manually edit results.

After execution:

1. Validate result schema.
2. Validate correctness.
3. Generate SHA256 manifest.
4. Generate machine-readable results.
5. Generate human-readable verdict.
6. Re-read the generated artifacts.
7. Check for accidental claim inflation.
8. State exactly what the run establishes.
9. State exactly what remains unestablished.

---

## 17. Final Referee Checklist

Before an agent says a benchmark is complete, it MUST answer:

- Are all competitors actually executable?
- Were they run?
- Did they receive identical canonical instances?
- Were outputs independently verified?
- Are solver versions recorded?
- Are compiler flags recorded?
- Is hardware recorded?
- Are timing boundaries explicit?
- Are generation and solve time separated?
- Are all seeds recorded?
- Are all instance hashes recorded?
- Are all solution hashes recorded where meaningful?
- Are failures preserved?
- Are historical results clearly separated from current results?
- Is the missing bit-packed implementation explicitly acknowledged if still absent?
- Has any SOTA language been accidentally introduced?
- Has any asymptotic claim been inferred from finite timing?
- Has any quantum-advantage claim been inferred from classical simulation?
- Can another agent reproduce the run from the artifacts?

If any answer is NO or UNKNOWN, the final verdict must disclose it.

---

## 18. Governing Principle

The repository follows:

~~~
CLAIM STRENGTH <= EVIDENCE STRENGTH
~~~

and:

~~~
SIM2XR simulation != formal proof
benchmark speedup != asymptotic proof
classical quantum simulation != quantum advantage
historical result != current reproduction
alignment != membership != validation
~~~

When in doubt, preserve the evidence and lower the claim rather than raising the claim to fit the evidence.
